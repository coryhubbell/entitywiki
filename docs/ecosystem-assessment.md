# EntityWiki ecosystem migration assessment — October 23, 2026

The migration covers the entire existing MediaWiki installation and every client, not only the MAXPlaces structured pilot. The original A2/Hosting.com database/files have **not** been obtained or restored. The protected Cloudways PHP app is a recovery destination. Live `entitywiki.org` and DNS remain unchanged.

The completed unauthenticated archive preserves **219 exposed pages and 1,046 exposed revisions** across the nonvirtual namespaces at its capture boundary: 144 main, 71 User, two Project and two Template pages. A User page is not an account, a main-namespace page is not necessarily a client, and a namespace with no exposed pages does not prove that its underlying subsystem or files are absent. These historical counts must not be substituted for a later consistent SQL baseline.

## Native reader and replacement boundary

First prove the complete MediaWiki recovery clone. Use that native system as the compatibility reader for historical revisions, diffs, discussion, templates/categories, files, permission-sensitive pages and system/API functions until the replacement has equivalent tested behavior. Keep recovery, schema upgrades and frontend replacement as separately checkpointed stages. This is a staging design boundary, not a deployed routing or DNS change.

The structured registry exposes one MAXPlaces profile and fixed pilot import/resolution paths. A separate generic captured-record store and authenticated legacy reader now preserve every captured page and namespace, with source-origin/wiki/page identity and complete captured revision metadata. See [all-client staging](all-client-staging.md). Its accepted company contract is not a lossless MediaWiki storage format. Migration needs a private ledger keyed by **source wiki/database identity + namespace + page ID**, recording original titles/URLs/revision IDs, preserved role, reviewed company/client/entity linkage, destination reader, evidence/restrictions and acceptance state. A business may own several pages; a template, contributor page or category must never become a client merely because it was captured. No merge based only on company names, city names or shared template use is accepted.

## Checks prepared while hosting access is pending

`scripts/restore-counts.mjs` emits SELECT-only SQL. Supply the complete actual table inventory with `--table-list`; otherwise it diagnoses only essential core tables. It counts every supplied custom table and conditionally adds 1.39 checks for template targets, source-page links, categories, redirects, interwiki records, logs, permissions, accounts, jobs and caches. Ordered row digests cover known optional core tables without emitting their private values. External content pointers and content addresses are emitted as digests, not raw paths. SQL output itself remains private recovery evidence.

The generator's optional columns were checked against the official `REL1_39/maintenance/tables-generated.sql` on October 23, 2026 (SHA-256 `88df4bd2ac7c67f4708345fbcc4c598d2867b9e48ed7d14cceb304f0753dbde9`). In particular, 1.39 `templatelinks.tl_target_id` joins `linktarget.lt_id`; old title-column assumptions are not used. Generated queries have not been executed against the unavailable original database. Present-but-incompatible schema errors must be investigated; missing optional tables are explicit diagnostics, not proof that the subsystem was preserved.

After source access: capture complete immutable SQL/files/configuration; establish its consistent baseline; restore into isolated staging; compare every table and storage dependency; test all clients/namespaces/history/permissions/URL classes; then assess replacement coverage. Counts and digests supplement the preserved recovery set and functional tests. Preexisting source inconsistencies must be recorded and distinguished from restoration damage.
